## Goal & Why

- **Goal**: (1) Run a mandatory empirical spike: invoke `claude --print` with progressively stripped environments to determine the minimum set of env vars required for subscription authentication. (2) Run a complementary spike to determine the exact command for `healthCheck()` (e.g. `claude whoami` or equivalent). (3) Author `sanitisedEnv(): NodeJS.ProcessEnv` in `src/adapters/claude.ts` using the confirmed allowlist. (4) Record the confirmed allowlist as **WS_02-D2-allowlist** in the CLAUDE.md Decision Log before T3 is signed off. (5) Author unit tests in `tests/adapters/sanitisedEnv.test.ts` proving each stripped var is absent and each required auth var is present.
- **Why**: `sanitisedEnv()` is the only defence against the Haiku path-leak class (spec §5.3) — the failure mode where ambient machine env vars (HOME, PWD, filesystem paths, user identity signals) bleed into tool-call arguments generated by the model. If the function strips too much, the only Phase 1 transport silently breaks. If it strips too little, path-leaking passes WS_03's functional tests but fails WS_09's contamination probes — and those failures are subtle and late. The empirical spike eliminates assumption risk at the earliest possible point. `healthCheck()` uses the same env, so the spike covers both concerns in one session.

## Expected Failures

- **EF1** Running `env -i claude --print` (fully stripped env) will almost certainly fail — not because of the prompt but because `PATH` is stripped, making the `claude` binary unfindable by the shell. The spike must always preserve `PATH` (or use the absolute path to `claude`). Note: `child_process.spawn` in Node does not rely on the shell for binary resolution when passed an absolute path — but for the spike probes run manually in a terminal, `PATH` must be included.
- **EF2** On macOS, `DYLD_LIBRARY_PATH` and `DYLD_INSERT_LIBRARIES` may be stripped by the OS's SIP (System Integrity Protection) mechanism before the subprocess even starts — so they may be absent from the env regardless of what `sanitisedEnv()` returns. Do not add them to the allowlist on the basis that they are "needed" if they are already OS-stripped.
- **EF3** If `claude --print` reads `HOME` to locate `~/.claude/` (where credentials are stored), stripping `HOME` will break auth silently — the subprocess will start but authentication will fail at the API layer (not at subprocess launch). The spike must distinguish between "subprocess launched" and "subprocess authenticated". Use a known-good prompt (`echo '{"type":"text","content":"ping"}' | claude --print`) and check both exit code and stdout content for a valid JSON response.
- **EF4** The allowed env vars may differ between macOS and Linux. The empirical spike is run on the dev machine (macOS per OS Version field). If the project later runs on Linux CI, `sanitisedEnv()` may need a platform branch. Flag this in WS_02-D2-allowlist if macOS-specific vars are in the allowlist.
- **EF5** `sanitisedEnv()` must return a plain object — not a reference to `process.env`. If it returns `process.env` directly (even filtered), mutations in the caller would affect the original env. The implementation must construct and return a fresh `Record<string, string>`.

## Test Strategy

- **Unit**: `tests/adapters/sanitisedEnv.test.ts` — pure function, no I/O, no mocks. Assert: (a) each var in the "stripped" list is absent from the returned object; (b) each var in the confirmed allowlist is present in the returned object (test with a mocked `process.env` that includes all required vars); (c) the returned type is a plain `Record<string, string>` — no undefined values in the returned object (either the key is present with a string value, or it is absent entirely). 100% branch coverage required.
- **Integration**: N/A in T3's test suite. The real integration proof is: `healthCheck()` in T4 uses `sanitisedEnv()` and returns `true` on the dev machine.
- **Contract**: The return value of `sanitisedEnv()` must be passable directly to `child_process.spawn`'s `env` option without modification. T4 enforces this contract at the TypeScript level.
- **Contamination/Isolation**: The WS_09 contamination probe (end of phase) will confirm that the sanitised env does not bleed path information into model outputs. T3's unit tests cannot prove this — they only prove the function's structural behaviour. The contamination proof is deferred to WS_09 by design.
- **Manual/spike**: The empirical spike is the primary validation for this task. See the Subtask Progress Table and the spike protocol below.

### Spike Protocol (mandatory — must complete before any code is written)

Run the following commands on the dev machine. Record every result in the Subtask Progress Table Notes column. The confirmed allowlist is the set of vars where removing any one causes `claude --print` to fail (non-zero exit code or empty/malformed stdout).

**Spike step 1 — baseline**: Confirm `claude --print` works in the normal env:
```
echo '{"type":"text","content":"ping"}' | claude --print
```
Expected: a raw JSON response. If this fails, stop — there is a pre-existing issue with the `claude` CLI installation.

**Spike step 2 — probe auth command**: Determine the correct `healthCheck()` probe:
```
claude whoami
```
If exit code 0 and output contains account information: `claude whoami` is the probe. If exit code non-zero or command not found: try `claude --version`, then `claude auth status` (if available). Record which command works and what exit code it returns when authenticated.

**Spike step 3 — progressive env stripping**: Start with a minimal env and add vars until the call succeeds:
```
env -i PATH="$PATH" HOME="$HOME" claude --print <<< '{"type":"text","content":"ping"}'
```
Then strip `HOME` and observe:
```
env -i PATH="$PATH" claude --print <<< '{"type":"text","content":"ping"}'
```
Then add additional candidate vars one at a time. Typical candidates that may be required: `HOME` (for config path), `USER` or `LOGNAME` (for identity), `TMPDIR` or `TEMP` or `TMP` (for temp files during auth), `XDG_CONFIG_HOME` (Linux), `ANTHROPIC_API_KEY` or similar credential env vars (if any). For each: test with it present vs. absent; record the result.

**Spike step 4 — confirm the Haiku path-leak class vars are absent in the final allowlist**: After the allowlist is confirmed, explicitly verify that the following vars are NOT in the allowlist (meaning they are stripped): `PWD`, `OLDPWD`, `SHELL`, `SHLVL`, `_` (last command), `TERM`, `TERM_PROGRAM`, `ITERM_*`, `TERM_SESSION_ID`, `COLORTERM`, `LS_COLORS`, `LSCOLORS`, `LESS`, `PAGER`, `EDITOR`, `VISUAL`, `MANPATH`, `JAVA_HOME`, `GOPATH`, `GOROOT`, `CARGO_HOME`, `RUSTUP_HOME`, `NVM_*`, `CONDA_*`, `VIRTUAL_ENV`, `npm_*`. If any of these are required by `claude --print` auth, record them explicitly with a note explaining why they are needed and what information they reveal — this is a known residual risk.

## Decisions Made

### WS_02-D2 — `sanitisedEnv()` Allowlist Determined Empirically; Recorded in Decision Log ✅ LOCKED (Architect, 2026-06-08)

**Decision**: The allowlist for `sanitisedEnv()` is not assumed from documentation — it is determined by running `claude --print` with progressively stripped environments and confirming that subscription authentication still holds. The resulting allowlist is recorded as WS_02-D2-allowlist in the CLAUDE.md Decision Log before WS_02 is signed off.

**Rationale**: Stripping too much silently breaks the only transport in Phase 1. Stripping too little defeats the purpose of the function. The risk is asymmetric: a broken transport is immediately visible (healthCheck fails); a path-leaking transport is subtle and only caught by WS_09's contamination probe. Empirical determination eliminates the assumption risk at the cheapest point in the build sequence.

**Rejected alternative — strip all env vars**: Risks silently breaking `claude --print` subscription auth, making Phase 1 transport unusable.

**Rejected alternative — strip only the vars listed in spec §5.3 by name without testing**: The spec names a class of vars, not an exhaustive list. Machine-specific vars (e.g. `ITERM_SESSION_ID`, Node version manager vars) are not enumerated in the spec. Testing is the only way to confirm the list is complete.

### WS_02-D-T3-01 — `sanitisedEnv()` Returns a Fresh Object, Never a Filtered Reference to `process.env` ✅ LOCKED (Architect, 2026-06-09)

**Decision**: `sanitisedEnv()` constructs and returns a new `Record<string, string>` each call. It does not return `process.env` or a filtered view of it.

**Rationale**: `process.env` is a shared mutable object. If callers receive a reference to it (even a filtered one via `Object.fromEntries`), mutations in one part of the codebase would affect the env passed to future subprocesses. A fresh object is the safe, pure-function contract.

**Rejected alternative — return `Object.fromEntries(Object.entries(process.env).filter(...))`: Still references the original values by value (strings are immutable), so mutations to `process.env` after the call would not affect the returned object. However, this approach is subtly coupled to the current state of `process.env` at call time, which is the correct behaviour — the concern is about the reference identity. This alternative is acceptable if the implementation is a one-liner; the key constraint is that undefined values are excluded from the output.

File: `tests/adapters/sanitisedEnv.test.ts`

> Note: These tests use a mocked `process.env` context. The recommended pattern is to save `process.env` before each test, assign a controlled mock object, run assertions, then restore. Use `beforeEach`/`afterEach` for this.

### T-1: stripped vars are absent from the return value (covers SC-3)

Set `process.env` to an object containing a sampling of Haiku path-leak class vars: `{ PWD: '/some/path', OLDPWD: '/other/path', HOME: '/home/user', SHELL: '/bin/zsh', ...plus all required auth vars }`. Call `sanitisedEnv()`. Assert `result.PWD` is `undefined`. Assert `result.OLDPWD` is `undefined`. Assert `result.SHELL` is `undefined`. Repeat for each stripped var confirmed in the spike. (The exact list of assertions depends on the spike results — the BSE fills in the specific stripped var names from WS_02-D2-allowlist.)

### T-2: required auth vars are present in the return value (covers SC-4)

Set `process.env` to an object containing all confirmed required vars (from WS_02-D2-allowlist) plus several Haiku leak vars. Call `sanitisedEnv()`. For each confirmed required var, assert `result[varName]` equals the value set in the mock. (The exact var names depend on the spike results.)

### T-3: Haiku leak class var absent even when present in process.env (covers SC-3)

Set `process.env.ITERM_SESSION_ID = 'fake-session-id'`. Call `sanitisedEnv()`. Assert `result.ITERM_SESSION_ID` is `undefined`. Repeat for a representative subset of the Haiku leak class. This confirms the function actively strips these vars, not just happens to not include them.

Call `sanitisedEnv()`. Assert the returned object is not `process.env` (`expect(result).not.toBe(process.env)`). Assert mutating `result` does not change `process.env`: set `result['__test_mutation'] = 'x'`; assert `process.env['__test_mutation']` is `undefined`.

### T-5: missing required var in process.env is handled without throwing (covers A1 edge case)

Remove a required auth var from the mock `process.env`. Call `sanitisedEnv()`. Assert the function does not throw. The missing var should either be absent from the result or present as an empty string — whichever the implementation chooses, it must be consistent and documented in the Decision Log.
